# HOI4 海軍哨戒任務の内部処理

> **innovative balance v13.00 対応版**  
> Workshop ID `820039020` の `common/defines/00_defines.lua` と、提供されたGhidraプロジェクト内の対象exeを照合した。処理構造・関数アドレスはexe、係数はMODの現在値を基準にしている。

## 0. 先に結論

海軍の哨戒任務は、単純な「探知値に比例して一定時間後に発見」という処理ではない。敵任務部隊に対して、次の処理を毎時行う。

1. 担当海域にいる敵任務部隊から追跡対象を1個選ぶ。
2. 艦隊・航空隊・レーダー・海軍情報差から、発見進捗の最低値 `B` を作る。
3. 哨戒部隊と敵部隊の探知・視認性・速度差から、毎時進捗 `Δ` を作る。
4. 進捗へ `Δ` を加算し、さらに `B` 未満なら `B` まで引き上げる。
5. それとは別に、毎時 **`p = Δ / 100`** の確率で100%発見へ飛ぶ抽選を行う。ここで `Δ` は「毎時何パーセントポイント進むか」なので、たとえば `Δ=10` なら `p=0.10`、すなわち毎時10%の即時完成抽選になる。
6. 抽選に当たらなくても、累積進捗が100%へ達すれば必ず完全発見となる。

つまり実体は、**進捗ゲージと早期発見乱数を併用した打ち切り付き確率過程**である。

さらに、相手が潜水艦だけの隠密任務部隊なら、通常の追跡を開始する前に専用の二重抽選を通す。どれほど探知性能を高めても、第1抽選がMODでは5%なので、純潜水艦を新規捕捉する機会は原則として毎時5%が上限になる。

完全発見は観測国側の共有状態として敵任務部隊へ記録される。その後は、哨戒部隊自身が交戦規定に従って海戦へ入る経路と、待機中の打撃部隊が100%発見を確認して出撃する経路に分かれる。

## 2. 担当海域と追跡対象の選択

### 2.1 一つの哨戒任務部隊が同時に追う対象は一つ

哨戒側は現在の追跡対象参照と発見進捗を保持する。追跡中の敵が海域外へ出る、外交関係が変化する、修理・戦闘・任務状態などの条件を満たさなくなる、または担当海域自体が変わると、対象参照と進捗は解除される。

対象を持っていない場合は、担当海域内の敵海軍を走査する。友軍・同国・非敵対・対象外状態などを除外し、候補のうち `FUN_140e448a0` が返す値の小さいものを優先する。この関数は海域／位置間の経路評価に使われており、実質的には**移動距離または到達コストの小さい候補を優先する**処理と読める。ただし、この補助関数の値をUI上の「距離」そのものと断定するところまでは未確認である。

水上艦を含む通常任務部隊には、純潜水艦用の初期抽選はない。候補条件を満たせば追跡対象になり、その後の0～100%進捗へ入る。

### 2.2 複数海域へ任務を出した場合

艦隊へ割り当てた海域数より哨戒任務部隊が少ない場合、任務部隊は担当海域を交代する。MOD値は次の通り。

```lua
MIN_HOURS_TO_SHUFFLE_NEWLY_ASSIGNED_PATROLS = 7 * 24
```

`FUN_140d034e0` は、任務部隊側の担当継続カウンタがこの値以上のものだけを再配置候補へ入れている。したがって、新しく海域を担当した哨戒部隊は、原則として**最低168時間＝7日間**はその担当から再シャッフルされない。

これは「一度見つけた敵を7日間追い続ける」という意味ではなく、哨戒部隊が不足しているときの**海域カバー担当の交代待ち時間**である。

### 2.3 UI上の推奨値は任務の実行条件ではない

MODには次の値もある。

```lua
SURFACE_DETECTION_STAT_FOR_SHIP_TO_BE_PATROL = 16
MIN_SHIP_COUNT_FOR_TASK_FORCE_ROLE_ASSIGNMENT = 2
MISSION_PATROL_SOFT_REQ_THRESHOLD_SURFACE_DETECTION = 22
```

前二つは任務部隊の自動役割・徽章判定、最後は任務アイコンへ警告を出すためのsoft requirementである。水上探知16未満、2隻未満、または水上探知22未満だから哨戒処理自体が止まる、というハード条件ではない。

## 3. 発見処理は `B` と `Δ` の二本立て

内部固定小数では `100000 = 1.0` で、発見進捗100%は `10000000` として保持される。以下ではすべて、UIで読めるパーセントポイントへ直して表記する。

```text
B = 艦隊・航空隊・レーダー・海軍情報差から作る発見進捗の最低値
Δ = 哨戒部隊と対象の性能差から作る毎時の進捗量

毎時:
    progress = progress + Δ
    progress = max(progress, B)
```

`B` は毎時間単純加算されない。「味方の航空哨戒が20ポイントを出しているから毎時+20」ではなく、現在進捗を最低20%まで押し上げる床として働く。一方、`Δ` は毎時間加算される。

そのため、同じ海域にいる別の友軍任務部隊・航空隊・レーダー・情報優位は初動を大きく短縮し、実際に追跡している哨戒部隊自身の探知・速度・視認性は、その後の継続的な進行速度を主に決める。

## 4. 初期／最低発見値 `B`

### 4.1 全体式

`FUN_140f6fa70` の構造は次の通り。

```text
Braw = BASE_SPOTTING
     + NavyBonus
     + AirBonus
     + RadarBonus
     + IntelBonus
     + NavalDominanceBonus

B = max(0, Braw * regional_or_weather_factor)
```

MODでは `NAVAL_DOMINANCE_SPOTTING_BONUS = 0` なので、通常は次の5項だけを考えればよい。

| 項目 | MOD値 | 最大寄与 |
|---|---:|---:|
| `BASE_SPOTTING` | 1 | 1ポイント |
| `BASE_SPOTTING_FROM_NAVY` | 10 | 10ポイント |
| `BASE_SPOTTING_FROM_AIR` | 20 | 20ポイント |
| `BASE_SPOTTING_FROM_RADAR` | 5 | 5ポイント |
| `BASE_SPOTTING_FROM_DECRYPTION` | 10 | ±10ポイント |

正の項だけなら、地域・天候補正前の名目上限は46ポイントである。海軍情報で相手に負けている場合、情報項は負値になりうる。

### 4.2 海域内の友軍海軍

対象の索敵用視認性を `Vsurf_target`, `Vsub_target`、海域内の友軍任務部隊の有効探知合計を `ΣDsurf_friendly`, `ΣDsub_friendly` とすると、次の飽和曲線になる。

```text
Xnavy = 0.1 * (
    Vsurf_target * ΣDsurf_friendly
  + Vsub_target  * ΣDsub_friendly
)

NavyBonus = 10 * (1 - 10^(-Xnavy))
```

`Xnavy >= 10` ではコード上10ポイントへ直接飽和する。ここで使われるのは追跡中の哨戒部隊だけではなく、対象海域にいる観測国側の友軍海軍の寄与合計である。

索敵用視認性のgetterは、任務部隊の水上／潜水視認性へ次を掛けた値を返す。

```text
VISIBILITY_MULTIPLIER_FOR_SPOTTING = 0.1
```

さらに帰港修理中なら、MODでは `NAVY_VISIBILITY_BONUS_ON_RETURN_FOR_REPAIR = 0.9` が掛かる。したがって、資料中の `V` は設計画面の生の視認性そのものではなく、これらを反映した**索敵用視認性**である。

### 4.3 航空隊

海域に対応する戦略地域の友軍航空隊について、航空隊ごとに概ね次の重みを作る。

```text
wingWeight = planeCount / 100
           * AIR_MISSION_SPOTTING_FACTORS[mission]
           * airMissionEfficiency

ΣAirSurface = Σ(wingWeight * aircraftSurfaceDetection)
ΣAirSub     = Σ(wingWeight * aircraftSubDetection)

Xair = 0.025
     * regionalAirEffectiveness
     * (Vsurf_target * ΣAirSurface + Vsub_target * ΣAirSub)

AirBonus = 20 * (1 - 10^(-Xair))
```

`Xair >= 10` では20ポイントへ飽和する。`regionalAirEffectiveness` は戦略地域側に保持される航空活動／有効範囲係数である。デコンパイル上、航空隊の実任務効率とは別に掛かっていることまでは確認できるが、UI上の単一のどの表示値と完全一致するかは未確定である。

MODで0以外の任務係数は次の通り。

| 航空任務 | 係数 |
|---|---:|
| 制空 | 0.50 |
| 迎撃 | 0.25 |
| 対艦攻撃 | 0.50 |
| 神風攻撃 | 0.25 |
| 機雷敷設 | 0.25 |
| 機雷掃海 | 0.50 |
| 偵察 | 1.00 |
| 海軍哨戒 | 1.50 |

航空の「海軍哨戒」は、海軍任務部隊の「哨戒」とは別の航空任務である。しかし、海軍側の発見値 `B` を支援する係数としては1.50で最も高い。逆に、港湾攻撃、近接航空支援、戦略爆撃などはこの表では0である。

### 4.4 レーダー

```text
RadarBonus = radarCoverage * 5
```

レーダー網が海域を100%カバーすれば最大5ポイントとなる。

### 4.5 海軍情報差

`FUN_1413bb000` は観測国と対象国の符号付き海軍情報差を使う。差を `d` とすると、MOD値では次の線形式になる。

```text
a = abs(d)

if a < 5:
    IntelBonus = 0
else:
    IntelBonus = sign(d) * 10 * min((a - 5) / (40 - 5), 1)
```

対応defineは次の通り。

```lua
NAVY_INTEL_BASE_SPOTTING_BONUS_MIN_INTEL_FOR_BONUS = 5
NAVY_INTEL_BASE_SPOTTING_BONUS_MAX_INTEL_FOR_BONUS = 40
BASE_SPOTTING_FROM_DECRYPTION = 10
```

情報差5未満では0、差40以上なら±10ポイントへ達する。defineコメントの「enemy decryption is subtracted」と実装が一致しており、相手の情報優位は初期発見値を下げる。

## 5. 毎時索敵進捗 `Δ`

### 5.1 探知を有効化する地域係数

まず `FUN_140f72920` が、哨戒側と対象側それぞれについて概ね次を作る。

```text
DetectionEnvironment = 0.10
                     + 0.10 * radarCoverage
                     + 0.25 * airSuperiority
```

担当海域内で任務部隊の編成／補給有効度が100%未満なら、この値全体へその有効度が掛かる。実際の水上・潜水探知statには、任務部隊、国、海域などの該当modifierも別途反映される。

レーダーと航空優勢は、前節の `B` だけではなく、この毎時進捗側の有効探知にも入る。特に航空優勢は、航空隊自身の任務係数による `AirBonus` とは別の寄与である。

### 5.2 水上探知項と潜水艦探知項

読みやすくするため、環境・補給・各種modifier適用後の探知を `D_eff` と書く。実装は概ね次の形である。

```text
surfaceTerm = (
    Vsurf_target * Dsurf_ours_eff
  - Vsurf_ours   * Dsurf_target_eff * 0.80
) * 1.00

subTerm = (
    Vsub_target * Dsub_ours_eff
  - Vsub_ours   * Dsub_target_eff * 0.80
) * 1.00
```

対応defineは次の通り。

```lua
SPOTTING_ENEMY_SPOTTING_MULTIPLIER_FOR_RUNNING_AWAY = 0.80
SPOTTING_MULTIPLIER_FOR_SURFACE = 1.00
SPOTTING_MULTIPLIER_FOR_SUB = 1.00
```

重要なのは、こちらの探知だけを一方向に見る式ではないことである。敵側の探知能力と、こちら自身の視認性が**逆探知／逃走項として減算**される。

したがって、哨戒艦の水上探知を上げるだけでなく、こちらの視認性を下げることにも意味がある。また、探知能力の高い敵艦隊は、こちらからの捕捉進行を遅らせる。

### 5.3 速度差

```text
speedDiff = ourSpeed - targetSpeed

if speedDiff >= 0:
    speedTerm = speedDiff * 0.20
else:
    speedTerm = speedDiff * 0.50
```

こちらが10だけ速ければ+2ポイント相当、10だけ遅ければ-5ポイント相当となる。追いつく側の利得0.20より、逃げられる側の損失0.50の方が大きい。

```lua
SPOTTING_SPEED_MULT_FOR_CATCHING_UP = 0.20
SPOTTING_SPEED_MULT_FOR_RUNNING_AWAY = 0.50
```

この速度は任務部隊の現在有効速度を読むため、損傷や速度modifierの影響を間接的に受ける。

### 5.4 哨戒効率、天候、夜間を含む最終式

MOD値を代入すると、最終形は次のようにまとめられる。

```text
Δ0 = 0.05 + surfaceTerm + subTerm + speedTerm

coordFactor = 1 + patrolCoordination * 0.50
Δ1 = Δ0 * coordFactor

Δ2 = Δ1 * (
    1
  + taskForceSpottingChanceModifier
  + regionalOrWeatherSpottingModifier
)

if night:
    Δ3 = Δ2 * (1 + nightSpottingChanceModifier)
else:
    Δ3 = Δ2

Δ = max(0.01, Δ3)
```

ここで `patrolCoordination` は国の「艦隊協調性」一般ではなく、艦艇statの**「哨戒効率」**である。日本語localizationは次の通り。

```text
STAT_NAVY_PATROL_COORDINATION: 哨戒効率
```

UI説明は「哨戒任務中、何事か発生した際の艦隊集合速度」となっているが、exeではこの値を `COORDINATION_EFFECT_ON_PATROL_SPOTTING` と掛け、索敵進捗全体へ乗算している。少なくとも今回の対象exeでは、哨戒効率は明確に**発見速度そのもの**を高める。

たとえば哨戒効率+20%なら、MODでは次の倍率になる。

```text
1 + 0.20 * 0.50 = 1.10倍
```

バニラdefineは係数1.00なので同じ+20%が1.20倍だが、このMODでは効果が半分である。

なお、`BASE_SPOTTING_SPEED = 0.05` のdefineコメントは「daily base spotting speed」と書かれている。しかし対象exeでは、毎時呼ばれる `FUN_140f744e0` がこの値を直接加算している。実装基準では**毎時の基礎加算**として扱うべきである。

## 6. 累積だけではない――毎時の早期発見乱数

`FUN_140f7ef10` は `Δ` を計算したあと、次の順番で処理する。

```text
progress += Δ
random = uniform integer 0..99999
progress = max(progress, B)

if progress >= 100:
    progress = 100
else if random * 100 <= Δ_internal:
    progress = 100
else:
    未完成のまま継続
```

通常表記へ直すと、各時間の早期完成確率はおおむね次になる。

```text
pEarly = clamp(Δ / 100, 0, 1)
```

ここで `Δ` は毎時のパーセントポイントである。

| `Δ` | 毎時の早期完成確率 |
|---:|---:|
| 0.01 | 約0.01% |
| 1 | 約1% |
| 5 | 約5% |
| 10 | 約10% |
| 25 | 約25% |
| 100以上 | 100% |

### 6.1 一定値と仮定したときの打切り時間

`B` と `Δ` が一定で、途中で対象が変わらないとする。乱数に一度も当たらなかった場合の強制完成時間は、概ね次になる。

```text
N = 1 + max(0, ceil((100 - max(B, Δ)) / Δ))
```

早期完成を含む平均時間は、`p = Δ / 100` として次の打切り幾何分布で表せる。

```text
E[T] = (1 - (1 - p)^N) / p
```

例として `B=20`, `Δ=10` なら、抽選に外れ続けても9時間目で100%に達する。各時間の早期完成率は10%で、平均完成時間は約6.13時間になる。

したがって、観測結果にかなりばらつきがあっても不具合とは限らない。同じ編成・同じ海域でも、早期完成乱数のため数時間で発見する場合と、累積上限近くまでかかる場合がある。

## 7. 純潜水艦任務部隊だけの初期二重抽選

候補が純潜水艦の隠密任務部隊である場合、通常の0～100%追跡へ入る前に次の二段階を通す。

### 第1抽選

```text
p1 = SUB_DETECTION_CHANCE_BASE = 5%
```

第1抽選に外れると、その潜水艦任務部隊はその時間の候補にならない。

### 第2抽選

第1抽選へ通った場合だけ、その潜水艦に対する `Δ` と `B` を計算する。`Δ <= 0` なら失敗し、正なら次の確率を作る。

```text
p2 = Δ * 2.0 + B^1.5 * 0.5
```

```lua
SUB_DETECTION_CHANCE_SPOTTING_SPEED_EFFECT = 2.0
SUB_DETECTION_CHANCE_BASE_SPOTTING_POW_EFFECT = 1.5
SUB_DETECTION_CHANCE_BASE_SPOTTING_EFFECT = 0.5
```

第2抽選にも成功して初めて、通常の追跡対象として登録される。したがって1時間当たりの新規捕捉確率は概ね次の通り。

```text
pAcquire ≈ 0.05 * clamp(p2 / 100, 0, 1)
```

たとえば `B=20`, `Δ=10` なら、

```text
p2 = 10*2 + 20^1.5*0.5
   ≈ 64.72%

pAcquire ≈ 5% * 64.72%
         ≈ 3.24% / 時間
```

`p2` を100%以上へ上げても、第1抽選が5%なので新規捕捉は最大約5%／時間である。これは、海戦中に潜水艦がrevealedになる処理とは別で、海戦前の哨戒対象取得ゲートである。

## 8. 10%・70%・100%で変わる情報状態

進捗が未完成で乱数にも外れた場合、`FUN_140c14a50` へ次の段階が記録される。

| 発見進捗 | 状態 | 表示内容の精度 |
|---:|---:|---|
| 0～10% | 0相当 | 実質未発見 |
| 10%超～70%以下 | 1 | 非常に粗い情報 |
| 70%超～100%未満 | 2 | 粗い情報 |
| 100% | 3 | 完全発見・正確な情報 |

MODの対応defineは次の通り。

```lua
SPOTTING_MISSION_DETECTION_THRESHOLD_LOW = 10
SPOTTING_MISSION_DETECTION_THRESHOLD_MEDIUM = 70
```

状態1・2では、艦数、主力艦数、戦力などの推定値にランダム誤差を付けるためのdefineも使われる。状態3になると正確な情報が得られ、打撃部隊の出撃条件にも使われる。

## 9. 発見後――哨戒自身と打撃部隊は別経路

### 9.1 哨戒部隊自身が交戦する場合

哨戒任務の毎時分岐は、交戦対象参照が設定されていると `FUN_140f7bd10` で次を再検証する。

- 同じ担当海域か
- 現在も敵対しているか
- 対象・自艦隊が戦闘、修理、移動などの不適格状態でないか
- 交戦規定と戦力判定を満たすか
- 必要な発見状態を満たすか

有効なら `FUN_140b93cd0` で海戦参加命令を出す。その後、哨戒側の交戦対象・追跡対象は解除される。

「交戦を避ける」に設定した哨戒部隊も索敵自体は行えるが、哨戒部隊自身が海戦を開始するための検証を通りにくくなる。小型・高速・低視認性の哨戒隊を生存させ、戦闘は打撃部隊へ任せる運用は実装構造と一致する。

### 9.2 打撃部隊

打撃部隊の任務関数 `FUN_140f77990` 自体は敵を索敵しない。先に艦隊単位の候補収集 `FUN_140cfca10` が、`FUN_140c107c0` の返値が3より大きい敵任務部隊、またはすでに始まっている参加可能な海戦を候補化する。次に `FUN_140d05140` が交戦規定ごとの戦力比を評価し、選んだ任務部隊へ `FUN_140f7eab0` で対象を渡す。

目標を受けた打撃部隊は `FUN_140f7bd10`／`FUN_140f82850` で、敵対関係、担当海域、航路制限、修理・交戦状態などを再検証する。対象が既存海戦に入っていない場合は完全発見状態3も再要求する。既存海戦へ参加できる対象では、その海戦を根拠に状態3の再確認を省く分岐がある。

```text
哨戒:
    敵を追跡 → 進捗と乱数 → 発見状態3を共有

打撃部隊:
    完全発見または既存海戦を候補化
    → 戦力比・交戦規定で割当
    → 出撃・移動
    → 到達時に海戦参加
```

よって「哨戒が敵を見つけた瞬間に、同じ関数が港の打撃部隊をワープ参加させる」わけではない。発見状態の共有と、打撃部隊の出撃・移動・海戦参加は別処理である。100%発見後も、距離、速度、航路、燃料、任務状態、交戦規定などで到着の成否や時間は変わる。

打撃部隊側の割当・出撃・海戦参加の詳細は、[打撃部隊任務の専用資料](./hoi4_naval_strike_force_mission_system.md)を参照。

完全発見時に呼ばれる `FUN_140d3af20` は、呼出先を追うと提督の進捗／経験更新系であり、海戦開始関数そのものではない。

## 10. Organizationと燃料は索敵式へ直接入るか

### Organization

`FUN_140f744e0` の毎時索敵式には、艦隊Organizationを直接読む処理は見つからない。以前解析した砲・魚雷命中率と違い、`currentOrg / maxOrg` をそのまま索敵速度へ掛ける経路ではない。

ただし、次の間接影響はありうる。

- 任務部隊の編成／補給有効度が低ければ、基礎探知係数全体が下がる。
- 損傷やmodifierで現在速度が落ちれば、速度差項が悪化する。
- Org不足で任務状態や交戦可能性が変われば、候補・交戦検証から外れる場合がある。

MODの任務中Org消費は次の通り。

```lua
ORG_COST_WHILE_MOVING[PATROL] = 0.2
ORG_COST_WHILE_MOVING_IN_MISSION_ZONE[PATROL] = 0.0
```

担当海域へ向かう移動中にはOrgコストがあるが、任務海域内の哨戒移動ではこのdefineによるOrgコストは0である。

### 燃料

燃料量そのものも `Δ` の直接変数ではない。MODの海軍哨戒燃料設定は次の通り。

```lua
MISSION_FUEL_COSTS[PATROL] = 1.0
MISSION_FUEL_COSTS_PRIO_FACTOR[PATROL] = 1.0
NNavy.FUEL_COST_MULT = 0.10
```

燃料不足で有効速度や任務遂行状態が悪化すれば間接影響が出る。ただし、このMODは `OUT_OF_FUEL_SPEED_FACTOR = -0.00` なので、少なくともこのdefineによる速度低下は実質0である。したがってバニラよりも、燃料切れが索敵速度差へ直結しにくい設定になっている。

打撃部隊は港で待機している間、MODでは次が0である。

```lua
STRIKE_FORCE_ON_BASE_FUEL_COST_FACTOR = 0.00
```

哨戒側は常時海上で燃料を使い、打撃部隊側は待機燃料を節約する、という役割分担が数値上も強い。

## 11. MODと現在のバニラの主要差

発見システムの大半はバニラと同じだが、哨戒運用へ直接効く差は二つある。

| define | 現在のバニラ | MOD v13.00 | 効果 |
|---|---:|---:|---|
| `BASE_SPOTTING_SPEED` | 0.00 | 0.05 | 毎時式へ基礎進捗を追加 |
| `COORDINATION_EFFECT_ON_PATROL_SPOTTING` | 1.00 | 0.50 | 哨戒効率の索敵倍率を半減 |

それ以外の今回の中心値、たとえば基礎発見1、海軍最大10、航空最大20、レーダー最大5、情報差最大±10、最低毎時進捗0.01、潜水艦第1抽選5%、速度差0.20／0.50、発見段階10／70／100などは、確認した現在のバニラと同じである。

MODの変更は、低性能な哨戒にもわずかな基礎進行を保証する一方、技術・ドクトリンなどで得る哨戒効率の伸びを弱める方向である。

## 12. 実戦上の読み替え

### 水上艦隊を早く見つけたい場合

優先度は概ね次のようになる。

1. 哨戒任務部隊の水上探知を上げる。
2. 哨戒部隊を高速化し、敵より遅くならないようにする。
3. 哨戒部隊自身の水上視認性を下げ、敵の逆探知減算を小さくする。
4. 海域のレーダーカバーと航空優勢を上げる。
5. 海軍哨戒機・偵察機などで初期値 `B` を押し上げる。
6. 海軍情報差を確保する。
7. 哨戒効率を上げる。ただしこのMODでは係数がバニラの半分。

特に速度項は非対称で、遅いことの罰0.50が速いことの利益0.20より大きい。探知だけ高い低速艦より、十分な探知を持つ高速・低視認性艦の方が安定しやすい。

### 潜水艦を見つけたい場合

潜水艦探知、航空哨戒、レーダー、初期値 `B` は第2抽選と通常進捗の両方を助ける。しかし純潜水艦への新規捕捉は、第1抽選5%を必ず通る。したがって探知を極端に上げても完全な決定論にはならず、良編成でも発見開始時刻に大きなばらつきが残る。

### 哨戒と打撃部隊の編成思想

発見処理だけを考えれば、哨戒部隊へ戦艦級の火力を積む必要はない。探知、速度、低視認性、生存性を優先し、交戦規定を抑えて、完全発見後の戦闘を港の打撃部隊へ任せる構成には合理性がある。

一方、哨戒部隊自身に敵を拘束させたいなら、発見性能だけでなく、交戦規定、最低限の戦闘力、到着する打撃部隊まで生き残る能力が必要になる。索敵式と交戦判定は別なので、「発見が速い」ことと「安全に接触を維持できる」ことは同じではない。

## 13. 別処理と混同しないための注意

- この資料の中心式は、敵の通常海軍任務部隊を発見する哨戒処理である。
- 輸送船団、兵員海上輸送、上陸船団には、`CONVOY_SPOTTING_SPEED_MULT`、`UNIT_TRANSFER_SPOTTING_SPEED_MULT`、`NAVAL_INVASION_SPOTTING_SPEED_MULT` などを使う別の初期発見・進捗経路がある。
- 海戦が始まった後に潜水艦がrevealedになる処理も別である。
- 航空任務の「海軍哨戒」は、海軍任務の「哨戒」ではない。ただし航空側は海軍側の初期値 `B` を支援する。
- 「水上探知16」「最低2隻」「soft requirement 22」はUI・役割推奨であり、任務実行のハード条件ではない。
